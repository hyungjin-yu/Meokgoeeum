# 먹괴음 (Meokgoeeum) — 개인 프로젝트

## 프로젝트 개요

- **목적/목표:** Steam PC 출시용 3D 실시간 액션 RPG 완성
- **플랫폼:** PC (Steam)
- **완성 기준 (MVP):** v0.1 — 이동 + 전투 + 색 복원 파동 + 먹괴음 1종이 돌아가는 프로토타입
- **팀:** 1인 개발 (기획·프로그래밍) + 디자이너 친구 합류 협의 중

## 기술 스택

- **엔진:** Unity 6.3 LTS
- **렌더 파이프라인:** URP (Universal Render Pipeline)
- **주요 패키지:** Addressables, New Input System, Cinemachine, VFX Graph, Timeline, NavMesh, Unity Behavior (Preview)
- **서드파티:** DOTween, UniTask
- **언어:** C# 전용 (Blueprint 없음)
- **세이브:** JsonUtility → `Application.persistentDataPath`

## 엔진 선택 배경 (중요)

- UE5 → Unity 6.3 LTS로 전환 결정 (2026-05-29)
- **전환 이유:** 1인 개발 + C# 친숙 + Asset Store + 빠른 이터레이션
- **URP 선택 이유:** HDRP는 1인 개발에 설정 부담이 크고, 이 게임의 핵심 연출(색 복원 파동)은 URP Shader Graph로 충분
- Lumen(UE5) → APV + Shader Graph로 대체. 스타일라이즈드 아트 방향으로 한계 희석

## 게임 핵심 컨셉 (빠른 파악용)

```
장르:  3D 실시간 액션 RPG
배경:  조선 풍 현대 도시 (회색조 → 색 복원)
주인공: 붓을 무기로 쓰는 성인 (어린 시절 기억을 잃은 상태)
적:    먹괴음 — 먹물 괴물 5종 (평/원/흡/분/광)
핵심:  적 처치 → 색 구슬 드랍 → 파동 연출로 색 복원 → 맵 회전
반전:  이 세계는 큐브 1개. 탑이 아니라 큐브 면을 순환하는 구조
보스:  포(鯆) — 핑크 돌고래, 3페이즈, 플레이어의 옛 친구
```

### 설계 우선순위
1. 혼자 빠르게 만들 수 있는가
2. 혼자 유지보수 가능한 복잡도인가
3. 디버깅이 쉬운가
4. 나중에 확장/개선 가능한가

### 설계 방식
- 단순한 버전 먼저, 필요하면 더 구조적인 버전 선택지 제시
- 더 나은 패턴이 있으면 제안해도 되지만 혼자 감당 가능한 수준으로

### 스크립트 기본값 변경 시 유의사항 (2026-08-16 추가)

- **`public` 필드의 기본값(`= 20f` 등)을 코드에서 바꿔도, 씬에 이미 배치된 오브젝트의 값은 자동으로 안 바뀐다.** Unity는 컴포넌트가 처음 추가될 때의 값을 그대로 직렬화해서 씬 파일에 저장하기 때문. (EnemyHealth maxHP, PaintableObject fadeDuration에서 반복된 패턴)
- 그래서 밸런스/타이밍 값을 코드에서 바꿀 때마다: **"이미 씬에 배치된 오브젝트도 Inspector에서 수동으로 값을 바꿔야 한다"는 걸 매번 명시적으로 안내할 것.** 빼먹으면 사용자가 "왜 안 바뀌지"하고 헷갈림

### 순차 효과 "타이밍이 안 보임" 버그 진단 원칙 (2026-08-18 추가)

- **여러 대상에 시간차를 두고 순차적으로 효과를 주는 시스템**(색 복원 파동처럼 거리순으로 퍼지는 연출, 나중에 만들 큐브 회전 연출·컷씬 등)에서 "순서 없이 동시에 일어나는 것처럼 보인다"는 리포트가 오면, **로직 버그로 단정하기 전에 먼저 이 비율부터 확인**: `개별 전환(페이드/트윈 등) 소요 시간` vs `대상 간 트리거 시간차`. 전자가 후자보다 길면 전환 구간이 서로 겹쳐서 육안상 동시로 보이는 것뿐 — 트리거 로직 자체는 정상일 가능성이 큼
- 실제 사례: [[changelog/2026-08-16_색복원파동-타이밍조정]] — 파동 트리거는 거리순으로 정확했지만(0.18/0.21/0.31/0.46s) `fadeDuration`(0.5s)이 트리거 시간차 총합(0.28s)보다 길어서 "버그"처럼 보였음
- 확인 절차: 진단 로그로 실제 트리거 시각을 먼저 찍어본다 → 트리거 자체가 순서대로면 로직은 정상, 튜닝(전환 시간 단축) 문제로 처리

### 피격/상태 변화 로깅 원칙 (2026-08-16 추가)

- **모든 `IDamageable.TakeDamage()` 구현체는 맞을 때마다 `Debug.Log`로 "누가, 얼마나 맞았고, 남은 HP가 얼만지" 찍는다** — 비주얼(HP바 등)이 아직 없는 v0.1 단계에서는 콘솔이 유일한 확인 수단. `PlayerHealth`, `EnemyHealth`가 이미 이 형식(`"{대상} 피격! 남은 HP: {현재}/{최대}"`)을 따름 — 새 체력 관련 스크립트(보스 등)도 동일 형식 유지
- 나중에 실제 HP바 UI가 생기면 로그를 지우는 게 아니라 **같이 유지** (콘솔 로그는 디버깅/QA용으로 계속 쓸모 있음)

### 코드 최적화 원칙 (2026-08-16 추가)

> "무조건 복잡하게 최적화"가 아니라 **"공짜로 얻을 수 있는 효율은 처음부터 챙기고, 병목이 확실한 곳만 신경쓴다"**. 필러 4(혼자서 완성 가능한 범위)와 충돌하면 필러 4가 우선.

- **매 프레임 비용이 반복 곱해지는 곳(적 여러 마리 × Update 등)은 처음부터 신경쓴다** — 나중에 적 개체 수가 늘어나면 그대로 병목이 되므로, 처음 짤 때 폴링 주기 다운샘플링(예: 매 프레임 대신 0.1~0.2초 간격) 같은 선택지를 기본으로 고려
- **자주 생성/파괴되는 오브젝트는 처음부터 풀링 구조 고려** — 색 구슬, 분열형 소형 개체, VFX 파티클처럼 반복적으로 Instantiate/Destroy될 게 뻔한 것들은 나중에 갈아엎기보다 지금 오브젝트 풀로 짜는 게 오히려 더 쉬움
- **머티리얼 인스턴스는 `renderer.material` 직접 접근보다 `MaterialPropertyBlock` 우선 검토** — 특히 색 복원 파동처럼 여러 오브젝트에 개별 파라미터를 줘야 하는 경우, 배칭/GPU 인스턴싱과의 호환성 때문에 중요
- **매 프레임 GC 할당(`new`, LINQ, 클로저 캡처 등)은 피한다** — Update()/FixedUpdate() 안에서 특히
- **자료구조 선택은 "왜 이걸 골랐는지" 한 줄이면 충분** — 완벽한 알고리즘을 찾으려 시간 쓰지 말고, O(n²)이 될 뻔한 뻔한 패턴만 피하는 수준으로 충분
- 확실한 병목인지 애매하면: 일단 단순하게 짜고 주석으로 "나중에 프로파일링 필요"만 남겨둔다 (→ [[30 플레이테스트 & 밸런싱 검증 계획]] Unity Profiler 활용)
