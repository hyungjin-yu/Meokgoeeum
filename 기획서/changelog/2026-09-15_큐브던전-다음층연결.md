# 큐브 던전 — 방D 클리어 시 "다음 층" 연결

## 배경

[[changelog/2026-09-15_큐브던전-웨이브스포너와장식]]까지 방A~D 웨이브/장식이 검증된 뒤, 사용자가 "다음꺼 시작해"로 방D 클리어 후 "다음 층" 연결에 착수 요청. 기존 [[CubeMapManager]]는 "층 하나 = 씬 하나"를 통째로 갈아끼우는 방식인데, 지금 큐브 프로토타입은 물리적으로 하나뿐인 큐브라 그 방식이 안 맞음 — 사용자에게 확인해서 **"같은 4개 면을 새 콘텐츠로 덮어씌우기"**로 결정.

## 아키텍처 변경 — 런타임/에디터 코드 분리

기존 `CubeFaceRoomBuilder.cs`(에디터 전용, `UnityEditor` API 사용)에 벽/스폰/장식 로직이 전부 들어있었는데, "방D 클리어"는 **게임플레이 중 실제로 트리거되는 런타임 이벤트**라서 에디터 전용 코드를 호출할 수 없음(실제 빌드에 `UnityEditor` 어셈블리가 없음). 그래서:

- **`Assets/Scripts/Level/CubeDungeonRoomKit.cs` 신규** — `GetFaceBasis`/`BuildFaceWall`/`BuildDoorWall`/`BuildRoom`/`BuildWaveSpawner`/`BuildMural`/`BuildRoomObstacle`/`BuildRoomGate`/`PopulateRoomA~D`/`BuildFullFloor`를 전부 여기로 이전. `UnityEditor` API를 전혀 안 써서(`cubeCenter`/`cubeHalfExtent`/`enemyPrefab`을 매개변수로 받도록 바꿈) 런타임에도 안전하게 호출 가능.
- **`CubeFaceRoomBuilder.cs`는 얇은 에디터 래퍼로 축소** — 씬 열기/저장, 큐브 리사이즈, 기존 테스트 몹 재배치, `EnemyPyeong.prefab` 로드(`AssetDatabase`)처럼 진짜 에디터 전용/최초 1회성 작업만 남기고, 실제 방 짓기는 `CubeDungeonRoomKit.BuildFullFloor()` 한 줄 호출로 대체. 최초 실행 시 `CubeDungeonProgressionManager`도 같이 씬에 심음.
- **`Assets/Scripts/Level/CubeDungeonProgressionManager.cs` 신규(런타임)** — 방D의 `RoomClearGate.OnCleared`를 구독. 클리어되면: 페이드아웃(있으면) → 기존 `DungeonRooms_Generated` 삭제 → `CubeDungeonRoomKit.BuildFullFloor()`로 같은 4개 면에 새 콘텐츠 재생성(층수에 비례한 HP 배율 적용) → 플레이어를 새 방A로 텔레포트(`CinemachineCore.OnTargetObjectWarped()`로 카메라에 순간이동 통지 — [[CubeMapManager]].TeleportPlayerToSpawnPoint()와 동일한 이유) → 페이드인 → 새로 생성된 방D 게이트를 다시 구독(재귀적으로 계속 작동).
- **`RoomClearGate.cs`에 `public event System.Action OnCleared` 추가** — 기존 `stairs`/`doorsToOpen`처럼 "무엇을 열지"를 미리 정해두는 방식과 달리, 클리어되는 순간 정확히 한 번 호출되는 범용 훅. 런타임에 매번 새로 생성되는 게이트라 Inspector로 미리 연결해둘 수 없는 이번 경우에 딱 맞음.

## 난이도 스케일링

`CubeDungeonProgressionManager.hpMultiplierPerFloor`(기본 0.15) — 층이 올라갈수록 `1 + 0.15×(층수-1)`만큼 적 최대HP 배율이 누적 증가. 2층=1.15배, 3층=1.30배 ... 콘텐츠 구성(방 레이아웃/적 배치/장식)은 층마다 동일 — 난이도 변주는 이번엔 HP 배율 하나로만 단순화.

## 검증

- 재컴파일 에러 없음. `CubeFaceRoomBuilder.BuildFromCLI()` 재실행 성공, `CubeDungeonProgressionManager`가 씬에 정상 생성되고 `cubePlanet`/`player`/`enemyPyeongPrefab`/`currentFloor=1` 전부 올바르게 채워짐 확인.
- **Play 모드에서 `HandleRoomDCleared()`를 리플렉션으로 직접 호출해 "다음 층 전환"을 강제 트리거** — `currentFloor`가 1→2로 증가, 새 `DungeonRooms_Generated`(자식 42개)가 생성됨, 새 `RoomClearGate_D`도 정상 존재, 플레이어가 정확히 방A 시작 위치 `(0,0,18)`로 복귀함을 확인.
- 새로 생성된 스포너의 `hpMultiplier`가 `1.15`로 정확히 적용됨을 확인 — 다만 검증 도중 예전에 삭제 요청한 구(舊) 오브젝트가 `Destroy()`의 지연 특성상 즉시 안 사라져서 `GameObject.Find()`가 옛 오브젝트(멀티플라이어 1)를 잘못 집어 "버그처럼" 보였음 → `Resources.FindObjectsOfTypeAll`로 전체를 훑어보니 새/구 오브젝트가 공존 중이었을 뿐 실제 값은 정확했음이 확인됨(이 자동화 환경이 CLI 호출 사이에 실제 프레임을 안 흘려보내서 지연 파괴가 안 끝난 것 — 이전부터 알려진 환경 한계, 실제 유저 플레이에선 문제 없음).
- Play 종료 후 씬이 저장된 1층 상태(`currentFloor=1`, 스포너 4개)로 깨끗하게 되돌아옴 확인 — 테스트 중 만든 2층 콘텐츠가 저장 파일을 오염시키지 않음.

## 한계

- 실제 유저가 방A→B→C→D를 전부 실시간으로 클리어해서 자연스럽게 다음 층으로 넘어가는 전체 흐름은 사용자가 직접 Play로 확인 필요 — 이번 검증은 마지막 트리거만 리플렉션으로 강제 실행한 것.
- 층마다 콘텐츠가 동일(HP 배율만 다름) — 나중에 방 레이아웃이나 적 구성을 층별로 다양화할지는 별도 논의 필요.
- `FadeManager.Instance`가 이 프로토타입 씬엔 없어서 실제로는 페이드 없이 즉시 전환됨(코드는 있으면 쓰도록 짜여있음, `GameSystems` 붙이면 자동으로 활성화됨).
