# 큐브 표면 보행 프로토타입 (에버플래닛 글로브 뷰 × 큐브)

## 배경

사용자가 방A~D 멀티룸 던전을 보고 "이걸 실제 큐브 전개도로 만들어서 큐브로 접고, 그 안에서 플레이하게 하고 싶다"고 제안. 구체적인 레퍼런스로 넥슨 '에버플래닛'의 "글로브 뷰"(둥근 행성 표면을 걷는 카메라 시점)를 큐브에 적용하고 싶다고 확인 — 플레이어가 큐브 바깥 표면을 걷다가 모서리를 넘으면 중력이 그 면 방향으로 90도씩 회전하는 방식.

[[05 맵 시스템 - 큐브 구조]]의 "이 세계는 큐브 1개, 면을 순환하는 구조"라는 반전을 지금처럼 씬 전환으로 추상화하는 대신 **말 그대로 눈에 보이게 구현**하는 것 — 기존 아키텍처(면마다 별도 씬 로드/언로드 + 계단으로 전환)를 통째로 바꾸는 큰 결정이라, 바로 전체를 갈아엎지 않고 독립된 테스트 씬으로 "느낌"부터 검증했다.

## 만든 것

`Assets/Scenes/SC_CubePrototype.unity` — 기존 게임 씬과 완전히 분리된 프로토타입 전용 씬(`CubePrototypeBuilder.cs`, 에디터 전용, 재실행 안전).

- **`CubeSurfaceWalker.cs`** — 플레이어가 큐브 중심 기준 "지금 위치에서 절댓값이 가장 큰 축"으로 현재 서있는 면을 계산하고, 그 면의 바깥쪽 법선을 향해 자세(up)를 서서히 정렬. 이동 입력은 카메라 방향을 현재 면의 접선 평면에 투영해서 계산.
- **`CubeSurfaceCamera.cs`** — 월드 고정 Vector3.up 대신 CubeSurfaceWalker가 계산한 "지금 이 순간의 표면 법선"을 카메라의 up 기준으로 삼아 추적. Cinemachine은 월드 up 고정을 강하게 전제해서, 검증 전까지는 별도의 간단한 스크립트로 분리.

## 버그 2건 — 둘 다 리플렉션 스텝 실측으로 발견·수정

**① CharacterController와 동적 재정렬의 충돌.** 처음엔 CharacterController.Move()를 썼는데, 면을 넘어가는 순간(up이 (0,1,0)→(0,0,1)로 바뀌는 순간) 플레이어가 의도와 무관한 축(월드 Y)으로 계속 미끄러지는 버그를 발견. 원인은 CharacterController가 슬로프/스텝 처리를 위해 내부적으로 "자기 컴포넌트의 위 방향"에 대한 가정을 갖고 있는데, 매 프레임 임의 축으로 재정렬하는 이 프로토타입 용도는 지원하지 않는 것으로 보임(Unity 커뮤니티에서도 잘 알려진 한계). **CharacterController를 걷어내고 transform.position을 직접 다루는 방식으로 우회.**

**② 콜라이더 없이 속도만으로는 표면에 못 붙음.** CharacterController를 뺀 뒤, 접지 시 속도를 0으로만 맞췄더니 실측 결과 매 프레임 아주 조금씩 표면 밑으로 파고들다가 결국 반대쪽 면까지 뚫고 지나가버리는 걸 확인(속도 기반 접지는 "충돌"이 실제로 막아줘야 완성되는데 콜라이더가 없어서 아무것도 안 막음). **매 프레임 이동 후 표면 축 좌표를 큐브 표면 위치로 직접 clamp**해서 해결.

## 검증

Play 모드 진입 후 `CubeSurfaceWalker.Update()`/`CubeSurfaceCamera.LateUpdate()`를 리플렉션으로 150회 반복 호출하며 좌표를 실측(이 환경의 Play 모드 실시간 진행 불가 문제 우회 — 이 세션에서 계속 써온 방식):

```
step0:   pos=(0.00, 5.98, 3.62)  normal=(0,1,0)  — 윗면
step15:  pos=(0.00, 4.80, 5.00)  normal=(0,0,1)  — 모서리 통과, +Z면으로 전환
step30~90: pos.z가 정확히 5.00에 고정된 채 Y가 4.8→-4.2로 하강 — +Z 옆면을 타고 내려감
step105: pos=(0.00, -5.01, 4.04) normal=(0,-1,0) — 두 번째 모서리 통과, 아랫면으로 전환
step120~149: pos.y가 정확히 -5.00에 고정된 채 Z가 계속 감소 — 아랫면을 걸음
```

윗면 → +Z 옆면 → 아랫면, 총 2번의 모서리를 자연스럽게 넘으며 매번 표면 좌표가 정확히 고정되고 법선이 90도씩 정확히 전환됨을 확인.

## 한계 / 다음 작업

- **실제 "느낌"은 미검증** — 좌표 정확성은 실측했지만, 이 환경은 Play 모드 실시간 재생이 안 되는 문제가 있어서 카메라 전환이 실제로 매끄럽게 보이는지, 조작감이 에버플래닛처럼 자연스러운지는 **사용자가 직접 Play로 확인해야 함**
- 카메라가 진행 방향과 거의 평행해질 때(면의 접선 투영이 0에 가까워질 때) 이동 방향이 불안정해질 수 있는 경우를 아직 실측 안 함 — 실제 플레이에서 카메라를 이리저리 돌리며 확인 필요
- 지금은 CharacterController/콜라이더 없이 직접 clamp하는 방식이라 다른 오브젝트와의 충돌(적, 장애물, 지형 요철)은 전혀 처리 안 됨 — "느낌 좋다"고 판단되면 Rigidbody 기반이나 커스텀 캡슐 캐스트로 재설계 필요
- 기존 6면 멀티룸 던전 콘텐츠(방A~D 등)를 이 방식에 어떻게 이식할지는 미정 — 완전히 새로 설계해야 할 가능성 높음(현재는 "평평한 방들의 연쇄"인데, 큐브 표면 보행은 "한 면 전체가 하나의 큰 야외 지형"에 가까운 그림이라 레벨 디자인 자체가 달라짐)
- 이 프로토타입은 기존 게임 씬(SC_Face_0~5, SC_Game)과 완전히 분리되어 있어 실제 게임 콘텐츠에는 영향 없음

## 후속 — 실제 플레이 피드백 반영 (같은 날)

사용자가 직접 Play로 테스트하면서 나온 리포트 3건을 순서대로 수정.

**① "움직이지도 않고 카메라도 안 움직이는데"** — 리플렉션 테스트용 `SetMoveInput()`만 만들어두고 실제 키보드 입력 연결을 깜빡함. 이 프로젝트는 Active Input Handling이 "Input System Package (New)"뿐이라(`ProjectSettings.asset`의 `activeInputHandler: 1`) 레거시 `Input` 클래스는 아예 동작 안 함 — `Keyboard.current`로 WASD를 직접 읽는 `ReadKeyboardInput()`을 추가.

**② "마우스로 카메라 좌/우 회전은 가능했음 좋겠어"** — 카메라가 플레이어의 forward를 그대로 따라가기만 해서 사용자가 직접 돌릴 수 없었음. 카메라가 독립적인 "궤도 방향(orbitForward)"을 소유하고, 마우스 X 이동으로 표면 법선 축 기준 회전시키도록 변경. Esc로 커서 잠금 해제하는 안전장치도 추가.

**③ "너무 획획 돌아가서 멀미난다" → "카메라를 평면 위에서 회전시킬 때도 90도씩 가는거야?"** — 처음엔 마우스 감도(3)가 델타 픽셀에 그대로 곱해져서 과도했던 걸로 오판하고 감도를 0.15로 낮추고 스무딩을 추가했는데, 사용자가 재확인한 결과 **같은 면 위에서 카메라만 돌려도 면 판정이 흔들리는 게 진짜 원인**이었음. 기존 "매 프레임 좌표로 어느 축이 제일 큰지" 계산 방식이 코너 근처가 아니어도 미세한 흔들림에 취약했던 것 — 사용자가 직접 "빈 오브젝트를 트리거로 써도 된다"고 제안, 그대로 채택:

- `CubeFaceZone.cs` 신규 — 면마다 트리거 콜라이더를 두고, `OnTriggerEnter`로 들어온 순간에만 `CubeSurfaceWalker.SetCurrentFaceNormal()`을 호출
- `CubeSurfaceWalker`는 이제 매 프레임 좌표 계산 대신 이 트리거 이벤트로만 `CurrentSurfaceNormal`이 바뀜 — 같은 면 위에서는 카메라를 아무리 돌려도 면 판정 자체가 절대 안 바뀜
- **버그** — 트리거 존을 `CubePlanet`(localScale=10,10,10)의 자식으로 붙였더니, `BoxCollider.size`가 부모 스케일까지 곱해진 로시(lossy) 스케일로 적용되어 실제로는 지정한 크기의 10배(예: (4,10,10)→(40,100,100))로 부풀어서 6개 존이 전부 겹쳐버림 — 시작하자마자 엉뚱한 면으로 순간이동하는 것으로 발견. 스케일 없는 별도 빈 오브젝트(`FaceZones`)를 부모로 써서 해결
- 트리거 이벤트가 발생하려면 최소 한쪽에 `Rigidbody`가 필요해서 플레이어에 킨매틱 Rigidbody 추가
- 검증: Play 모드에서 `Physics.simulationMode = SimulationMode.Script` + `Physics.Simulate()`로 물리 스텝을 수동 강제하며(트리거 이벤트는 일반 좌표 이동과 달리 물리 시뮬레이션 자체가 돌아야 발생 — `Physics.SyncTransforms()`만으론 부족함을 이번에 확인) 직접 +Z 존으로 순간이동시켜 `CurrentSurfaceNormal`이 정확히 전환됨을 실측 확인

## 교훈

- 부모-자식 스케일 상속은 Transform 위치뿐 아니라 **Collider 크기에도** 그대로 곱해진다 — 스케일이 있는 오브젝트 밑에 콜라이더를 새로 붙일 땐 항상 의도한 월드 크기가 맞는지 실측할 것
- 트리거 이벤트(`OnTriggerEnter`)는 좌표 이동만으론 안 나고 실제 물리 시뮬레이션 스텝이 필요하다 — 이 환경처럼 Play 모드 실시간 진행이 막혀있을 때 트리거를 검증하려면 `Physics.simulationMode = SimulationMode.Script`로 바꾸고 `Physics.Simulate()`를 수동 호출해야 함(`Physics.SyncTransforms()`는 레이캐스트/오버랩 쿼리에는 충분하지만 트리거 콜백 디스패치는 안 해줌)
- 증상만 보고 원인을 어림짐작하지 말고(감도 문제로 오판했다가 사용자 재확인으로 진짜 원인이 다른 곳에 있었음을 알게 됨), 사용자가 재현 조건을 구체적으로 짚어줄 때까지 기다렸다가 정확히 진단할 것
