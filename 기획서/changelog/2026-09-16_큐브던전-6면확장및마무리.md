#기획 #먹괴음 #changelog

# 큐브 던전 마무리 — 6면 확장(방E/F) + 페이드 연출 + 평지 던전 안전성 재확인

## 배경

어제(9/15) 큐브 던전 포팅 작업 뒤 남겨뒀던 "다음 순서" 4개 항목(±X 면 용도, 층별 콘텐츠 다양화, 전환 페이드, 평지 던전 안전성 재확인)을 오늘 마무리. ±X 면 용도를 논의하다가 "E/F 방이 추가되면서 던전이 하나의 큐브가 되는 것"으로 방향이 확정되면서, 오늘의 핵심 작업은 **큐브 6면 전부를 던전 방으로 쓰는 확장**이 됨.

## 큐브 6면 확장 (핵심 작업)

### 오해 정정

처음엔 "큐브 토폴로지 자체를 원통 등으로 바꾸자"는 뜻으로 잘못 이해해서 기존 이동/면전환/방빌더 시스템 전체 재작업이 필요한 줄 알고 사용자에게 확인까지 받았는데, 사용자가 "정확히는 E/F 방이 추가되면서 던전이 하나의 큐브가 되는거야"로 정정 — 실제로는 **큐브 모양은 그대로 두고, 안 쓰던 ±X 두 면을 실제 던전 방(E, F)으로 편입시켜서 한 층이 6면 전부를 쓰게** 하는 것이었음. 다행히 정육면체의 면-인접 그래프(팔면체 그래프, 각 면이 반대편 1개 빼고 나머지 4개와 인접)는 항상 6면을 한 바퀴 도는 고리(해밀턴 순환)를 가질 수 있어서, 이동/면 전환 수학([[CubeSurfaceWalker]], [[CubeEnemyBase]], `GetFaceBasis`/`BuildFaceWall`)은 전혀 안 건드리고 **방 배치/문 배선만 확장**하면 되는 걸로 확인 — 우려했던 것보다 훨씬 작은 작업.

### 경로 설계

순서: **A(+Z)→B(+Y)→E(+X)→C(-Z)→D(-Y)→F(-X)** — 각 면의 u,v축이 항상 월드 좌표축과 정확히 일치한다는 사실("면 법선 n의 +u/-u/+v/-v 방향 이웃 면의 법선은 각각 u/-u/v/-v 그 자체")을 이용해 손으로 유도. 각 방의 문 배선표(어느 쪽이 진입/진출/막힘인지)는 [[CubeDungeonRoomKit]] 클래스 doc에 전부 기록해둠. F→A로 돌아가는 6번째 간선은 일부러 물리적 문을 안 냄 — F 클리어 시 기존 방을 통째로 지우고 새 A를 지어 텔레포트하므로, 그 순간엔 걸어서 갈 옛 A 자체가 없음(기존 D의 "다음 층 종착점" 역할을 그대로 F가 승계).

### 코드 변경

- **`CubeDungeonRoomKit.BuildRoom()`을 4방향(±U/±V) 전부 `WallMode`를 받도록 확장** — 예전엔 v±에만 문을 낼 수 있었고 u±는 항상 통짜로 막혀있었음("링에 안 쓰는 면과 맞닿는 쪽"이라서). 이제 6면을 다 쓰면서 u±에도 실제 이웃 방이 생기므로, `BuildDoorWall()`도 축 하나(v)만 처리하던 걸 U/V 어느 쪽이든 처리하도록 일반화(`WallSide` enum + 고정축/따라가는축 역할을 스왑하는 로컬 함수).
- `PopulateRoomE`/`PopulateRoomF` 신규(원본 [[MultiRoomFloor1Builder]] 패턴 재사용 — E는 평×1+1 2웨이브+벽화 2개, F는 평×2+2 클라이맥스+벽화 2개로 D의 옛 클라이맥스 역할 승계). 기존 `PopulateRoomD`는 중간 방 수준(평×2+1+장애물 1개)으로 축소.
- `BuildFullFloor()`를 6방 전부 짓도록 재작성, 손으로 유도한 문 배선표를 그대로 코드에 반영.
- `CubeDungeonProgressionManager`가 이제 `"RoomClearGate_F"`(예전엔 D)를 찾아 다음 층 전환을 구독.
- `CubeFaceRoomBuilder.RelocateExistingTestMobsToPlusX()` → `RemoveExistingTestMobs()`로 교체 — ±X 자리가 이제 실제 방(E/F)이라 안 쓰는 AI 검증용 테스트 몹 6개(5종+구프로토타입)를 그냥 정리함(옮기지 않고 삭제 — 이미 방A~F 실던전에서 반복 검증됐으므로 참고 목적은 달성됐다고 판단).

### 검증

- 재컴파일 에러 없음, `BuildFromCLI()` 재실행 성공(테스트 몹 6개 정리 로그 확인).
- 게이트 6개(A~F) 전부 존재, F만 `doorsToOpen=0`(의도된 것) 확인.
- Play 모드에서 `CubeSurfaceWalker.WouldCollide()`를 리플렉션으로 직접 호출해 **손으로 유도한 문 배선표를 전수 검증**:
  - 5개 게이트 문(A→B, B→E, E→C, C→D, D→F)이 잠긴 상태에서 전부 막힘 확인
  - 5개 입장 측(B/E/C/D/F의 진입 쪽)이 전부 안 막힘(통과 가능) 확인
  - A의 막힌 3면(→E, →F, →D 방향)이 전부 제대로 막힘 확인
  - 검증 도중 테스트 스크립트 자체의 단위 실수(방 크기 `RoomHalf=15`를 큐브 크기 `CubeHalfExtent=17`로 잘못 대입) 두 번 발견 → 정정 후 전부 정상 확인. 실제 게임 코드엔 버그 없었음.

## 층 전환 페이드 연출

[[FadeManager]]가 SC_CubePrototype 씬엔 원래 없어서(평지 던전 SC_Game의 GameSystems에만 있었음) `CubeDungeonProgressionManager`의 층 전환 페이드 코드(`FadeManager.Instance` null 체크는 이미 있었음)가 발동을 안 하고 있었음. `CubeFaceRoomBuilder`가 씬 세팅 시 `FadeManager`가 없으면 자동으로 추가하도록 수정 — `FadeManager`는 `Awake()`에서 자기 캔버스를 코드로 직접 만들어서 GameObject 하나만 있으면 충분함.

## 평지 던전 안전성 재확인

어제 코드 리뷰로만 "안전하다"고 판단했던 걸 오늘 실제로 `SC_Game`을 열어 Play로 확인:
- `BrushWeapon.ownsInputActions = False` 확인 — `PlayerController`와 정상적으로 InputActions 공유 중(큐브 모드 코드 경로가 안 타는 것 확인).
- `RoomClearGate.AnyEnemyAlive()`를 4개 게이트(A~D) 전부에 리플렉션으로 직접 호출 — 예외 없음, `ICubeFaceMob` 체크 추가가 평지 던전 오브젝트를 만나도 그냥 조용히 스킵함을 확인.
- 세이브/로드(`SaveManager`, `ColorSystemManager`), `EncounterSpawner` 웨이브 진행 등 기존 흐름 전부 정상 작동, 콘솔에 에러 없음.

## 한계

- **층별 콘텐츠 다양화**는 오늘 손 안 댐 — 6방 확장 자체가 사실상 이 항목의 큰 부분(더 이상 "4방 반복"이 아니라 "6방을 도는 온전한 큐브")을 흡수했지만, 층이 올라가도 방 레이아웃/적 종류는 여전히 동일(HP 배율만 증가)이라 "매 층이 다르게 느껴지는" 진짜 다양화는 아직 미착수.
- 사용자가 실제로 방A→B→E→C→D→F를 전부 걸어서 클리어하는 전체 흐름은 아직 실제 플레이로 확인 안 됨 — 오늘 검증은 문 배선/충돌만 리플렉션으로 정밀 검사한 것.
