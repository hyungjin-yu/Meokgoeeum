# 먹괴음 5종 AnimatorController 연결

## 배경

프리팹에 실제 모델과 Avatar까지는 연결됐지만, Idle 상태로 가만히 서있기만 했다. `EnemyPyeong.OnAttackWindupStart`/`OnAttackHit` 등 기존 코드에 이미 "VFX/애니메이션은 나중에 이 이벤트를 구독해서 붙이면 됩니다"라고 주석으로 남겨둔 훅이 있었는데, 이번에 실제로 애니메이션을 연결했다.

## 애니메이션 클립 선정

에셋스토어 팩(Kevin Iglesias, Human Melee Animations)에 던지기/시전 계열 클립이 따로 없어서(Unarmed 펀치/킥뿐), 종별 테마에 맞게 최대한 자연스러운 동작을 골라 매칭:

| 종류 | Idle | Move | Attack/Special |
|------|------|------|------|
| 평 | Idle01 | Walk01_Forward | AttackPunch01_R |
| 원 | Idle01 | Walk01_Forward | AttackPunch01_L (원거리형이라 유일하게 멀쩡한 왼손으로) |
| 흡 | Idle01 | Walk01_Forward | (공격 없음) Special=CombatIdle01 (흡수 중 "집중" 자세) |
| 분 | Idle01 | Walk01_Forward | AttackPunch02_R |
| 광 | Idle01 | Walk01_Forward | AttackKick01_R (범위형이라 더 크게 휘두르는 킥으로) |

Idle/Walk/CombatIdle 전부 `isLooping=true`로 이미 저작돼있어서 별도 루프 설정 불필요, Attack류는 `isLooping=false`(원샷) 확인.

## AnimatorController 구조

5종 전부 동일한 파라미터·상태 이름을 쓰도록 통일(값만 다름) — `Assets/Animations/Enemies/Enemy{Pyeong,Won,Heup,Bun,Gwang}.controller`:

- 파라미터: `Moving`(Bool) / `Attack`(Trigger) / `Special`(Bool)
- 상태: `Idle`(기본) / `Move` / `Attack` / `Special`
- Idle ↔ Move: `Moving` bool로 전이 (0.15초 블렌드, exit time 없음)
- AnyState → Attack: `Attack` 트리거 발동 시 즉시 전이(0.05초, 끼어들기)
- Attack → Move/Idle: 클립이 90% 재생된 뒤(exitTime=0.9) `Moving` 값에 따라 분기
- AnyState → Special: `Special`==true일 때 전이
- Special → Move/Idle: `Special`==false && `Moving` 값에 따라 분기

흡만 Attack을 쓰지 않고(비공격 유닛이라 실제로 트리거 안 함) Special을 쓰고, 나머지 4종은 반대로 Attack만 쓰고 Special은 미사용 — 구조는 5종 다 동일하게 만들어서 쓰지 않는 상태/파라미터가 있어도 무해하게 놔뒀다(코드가 5종 전부에서 똑같이 동작하도록 통일하는 게 개별 최적화보다 유지보수에 유리하다고 판단).

## C# 연결

- `EnemyBase.Awake()`에서 `animator = GetComponentInChildren<Animator>()` — 모델이 자식이라 재귀 탐색 필요
- `EnemyBase.LateUpdate()`에서 매 프레임 `Moving` bool을 agent 실속도 기준으로 갱신. 각 서브클래스의 상태 enum(Chase/Retreat/SeekHealArea 등 이름이 다 다름)을 직접 참조하는 대신 "지금 실제로 움직이고 있는가"라는 물리적 사실 하나로 통일해서 5종 전부 안전하게 재사용
- `EnemyPyeong`/`EnemyWon`/`EnemyBun`/`EnemyGwang`의 `EnterAttackWindup()`에 `animator?.SetTrigger("Attack")` 추가 (기존 `OnAttackWindupStart` 이벤트 발동 직전)
- `EnemyHeup`의 흡수 시작/종료 지점에 `animator?.SetBool("Special", true/false)` 추가

## 버그 발견·수정

**"IsStopped can only be called on an active agent that has been placed on a NavMesh"** — Animator 동작을 검증하려고 Play 모드에서 프리팹을 NavMesh 없는 허공(y=10)에 스폰해서 테스트했는데, `EnemyBase.LateUpdate()`가 `agent.enabled`만 확인하고 `agent.isOnNavMesh`는 확인 안 해서 매 프레임 콘솔에 에러가 찍힘. `agent.enabled`가 true라도 NavMesh 위에 아직 안 올라간 상태(스폰 직후 워프 전 등)에서 `isStopped`/`velocity`에 접근하면 예외가 난다는 걸 테스트 중에 직접 재현해서 발견 — `agent.isOnNavMesh` 조건을 추가해서 수정.

## 검증

Play 모드에서 5종 프리팹을 전부 스폰해 초기 상태가 `Idle`인지 확인, `Animator.Update()`를 수동으로 여러 스텝 강제 진행시키며 트리거·bool 전이가 실제로 작동하는지 검증:
- `Attack` 트리거 → 즉시 `Attack` 상태 전이 확인 (4종)
- `Moving=true` 상태에서도 `Attack` 상태 유지(exit time 전까지 공격이 우선됨) 확인 — 의도한 동작
- `Special=true` → `Special` 상태, `Special=false && Moving=true` → `Move` 상태로 정상 복귀 확인 (흡)

(참고: 별도 CLI 호출 사이의 실제 시간 간격 동안 Play 모드 시뮬레이션이 거의 진행되지 않는 현상을 겪었으나, `Animator.Update()`를 한 eval 호출 안에서 연속 호출하는 방식으로 전이 로직 자체의 정확성은 확실히 검증함 — 이 현상 자체는 자동화 환경의 타이밍 특성으로 추정되며 게임 자체의 문제는 아님)

## 교훈

- **자동화 테스트로 실제 게임 코드의 버그(NavMesh 미탑재 시 예외)를 하나 더 잡았다** — 정상 스폰 경로에서는 안 드러날 수 있는 엣지 케이스라도, "일부러 비정상적인 조건(NavMesh 없는 위치)에서 스폰해보는" 테스트가 의외의 실전 버그를 드러낼 수 있음
- Unity `Animator.Update(deltaTime)`을 수동으로 호출하면 Play 모드의 자동 프레임 진행과 무관하게 애니메이터 상태머신을 결정적으로(deterministic) 검증할 수 있다 — CLI 자동화로 애니메이터 로직을 테스트할 때 유용한 패턴
- 5종 전부 같은 파라미터/상태 이름 구조로 통일해두면, 일부만 쓰는 파라미터(흡의 Special, 나머지의 Attack)가 있어도 코드/그래프를 종별로 분기할 필요 없이 재사용 가능
