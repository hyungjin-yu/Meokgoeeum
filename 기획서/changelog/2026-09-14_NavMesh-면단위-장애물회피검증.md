# NavMesh — 면 단위 베이크로 실제 장애물 회피까지 검증

## 배경

[[changelog/2026-09-12_NavMesh-비Y업면-검증]]에서 "회전된 부모에 `NavMeshSurface`를 붙이면 비Y업 면도 구워진다"까지는 확인했지만, 그때는 장애물 없는 평면이었다. 실제 던전 방에는 장애물(기둥, 벽 등)이 있으므로, 오늘은 **장애물을 실제로 피해서 길을 찾는지**까지 검증했다 — 이게 확인돼야 기존 `EnemyPyeong` 등의 NavMeshAgent AI를 큐브 면 구조로 옮기는 작업을 시작할 수 있다.

## 삽질 — asmdef 참조 누락

`Unity.AI.Navigation.NavMeshSurface`를 쓰는 에디터 스크립트를 작성했는데, 컴파일 에러(`CS0234: The type or namespace name 'AI' does not exist`)가 남. 어제 `eval`로 같은 타입을 문제없이 썼던 것과 대조적이었는데, 원인은 `eval`은 넓은 어셈블리 참조로 동적 컴파일되는 반면, 실제 스크립트 파일은 `Meokgoeeum.Editor.asmdef`의 명시적 `references` 목록에 있는 어셈블리만 참조할 수 있기 때문이었다. `Unity.AI.Navigation`/`Unity.AI.Navigation.Editor`를 참조 목록에 추가해서 해결.

## 결과물

`Assets/Scripts/Editor/CubeFaceNavMeshTestBuilder.cs` 신규 — `SC_CubePrototype.unity`의 +Z 면(기존 [[CubeFaceLockedMob]] 테스트 몹이 있는 면)에 `FaceNavRoot_PlusZ`를 추가:

- 면 전체(20x20)를 덮는 바닥 평면
- 면 한가운데를 막는 4x4x3 장애물 기둥
- 이 루트 오브젝트에 `NavMeshSurface`(`collectObjects=Children`)를 붙여서 베이크

## 검증 결과

장애물을 사이에 둔 양쪽 지점(로컬 (-6,0,0)과 (6,0,0))으로 `NavMesh.CalculatePath()`를 호출:

- `path.status = PathComplete`
- corner 4개(직선 2개가 아니라 우회 경로) — `(-6,0,10.08) → (-2.17,2.67,10.08) → (2.33,2.67,10.08) → (6,0,10.08)`
- Z좌표는 시종일관 면 위(10.08 근처)에 고정된 채, 장애물을 피해 Y축 방향으로 우회 — **장애물 회피가 면 밖으로 새지 않고 정확히 그 면 안에서만 일어남**

## 결론

큐브 면 구조에서 실제 장애물이 있는 방을 NavMeshAgent 기반 몹으로 돌아다니게 만드는 게 아키텍처적으로 확실히 가능하다는 걸 확인. 남은 건:

1. `NavMeshAgent` 실제 이동/회전은 여전히 이 환경에서 자동 검증 불가(기존 한계) — 사용자 Play 테스트 필요
2. 실제 던전 빌드 스크립트(`Floor1CorridorBuilder` 등)의 `bake_navmesh`(레거시) 호출을 `NavMeshSurface` 방식으로 교체
3. `NavMeshAgent.updateRotation`을 끄고 face normal 기준 수동 회전 처리가 필요할 가능성(아직 미검증)

## 후속 — 실제 EnemyPyeong 배치 + updateRotation 방어 코드 (같은 날 이어서)

위 3번 리스크를 실제로 검증하려고 진짜 `EnemyPyeong.prefab`을 `FaceNavRoot_PlusZ`에 배치해봤다.

- `NavMesh.SamplePosition()`으로는 배치 위치가 유효한 navmesh 지점이라고 나오는데도, `NavMeshAgent.Warp()`/`SetDestination()`은 (컴포넌트를 껐다 켜도) 계속 실패(`isOnNavMesh=False`) — 어제와 동일한 환경 한계로 판단, 더 파고들지 않음.
- 그래서 실제 이동 검증은 포기하고, **미리 예상되는 리스크(③번)를 방어 코드로 선반영**하기로 함 — `EnemyBase.cs`에 `SetFaceUp(Vector3 up)` 신규 public 메서드 추가. 호출하면 `agent.updateRotation=false`로 끄고, `LateUpdate()`에서 `desiredVelocity`를 면에 투영한 뒤 `faceUp`을 up으로 삼아 직접 `Quaternion.RotateTowards`로 회전시킴([[CubeSurfaceWalker]]의 모서리 통과 로직과 같은 발상). **호출 안 하면(기존 5종 몹 전부) 지금까지와 완전히 동일하게 동작** — opt-in이라 평지 던전엔 전혀 영향 없음.
- **버그 발견·수정** — `SetFaceUp()`을 에디터에서 `Instantiate` 직후 바로 호출했더니 `agent` 캐시 필드가 아직 `null`(Awake가 에디터 모드에서 안 돎)이라 `updateRotation`이 안 꺼지는 걸 실측으로 발견. `agent ?? GetComponent<NavMeshAgent>()`로 즉시 컴포넌트를 다시 가져오도록 방어 코드 추가해서 해결 — 호출 순서와 무관하게 항상 먹힘.
- `CubeFaceNavMeshTestBuilder.cs`에 실제 `EnemyPyeong` 배치 + `SetFaceUp()` 호출 + 플레이어 `Player` 태그 설정까지 편입해서, 재실행 한 번으로 전부 재현되게 정리함.

**여전히 미검증**: 이 회전 코드가 실제 Play에서 자연스럽게 도는지는 사용자가 직접 확인해야 함 — 이 환경은 NavMeshAgent의 실시간 이동/회전을 재현할 방법이 없음.
