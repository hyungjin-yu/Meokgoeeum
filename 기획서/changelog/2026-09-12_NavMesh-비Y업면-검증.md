# NavMesh — 윗면이 아닌 큐브 면에서도 동작하는지 검증

## 배경

기존 `EnemyPyeong` 등 5종 먹괴음은 전부 `NavMeshAgent` 기반([[Assets/Scripts/Enemies/EnemyBase.cs]] — `[RequireComponent(typeof(NavMeshAgent))]`). [[changelog/2026-09-12_큐브면고정몹-공격판정검증]]에서 검증한 "면 고정" 규칙을 실제 던전(SC_Face_0 방A~D)에 적용하려면, 이 몹들이 큐브의 윗면(+Y)이 아닌 옆면/아랫면(법선이 월드 Y축이 아닌 면)에서도 정상적으로 길찾기를 할 수 있는지 확인이 먼저 필요했음.

## 검증 방법

`Assets/Scenes/_ScratchNavMeshTest.unity`(검증 후 삭제, 커밋 안 함)에 수평 기준 평면(원점)과 수직 평면(월드 (50,0,0), normal=+Z — 큐브 옆면 상황을 그대로 재현)을 만들어 두 가지 베이크 방식을 비교:

1. **레거시 전역 베이크** (`bake_navmesh` CLI 커맨드 → `UnityEditor.AI.NavMeshBuilder`, 이 프로젝트가 지금 실제로 쓰는 방식)
2. **`NavMeshSurface` 컴포넌트 베이크** (`com.unity.ai.navigation` 패키지 — 이미 설치돼 있었음, 지금까진 안 쓰고 있었음)

## 결과 — 확인됨

- **레거시 전역 베이크는 수직면을 완전히 무시함.** `NavMesh.CalculateTriangulation()` 결과: 수평면 근처 정점 16개(정상), 수직면(월드 +Z 법선) 근처 정점 **0개**. 레거시 베이크는 슬로프를 항상 월드 Y축 기준으로 계산해서, 법선이 Y에서 크게 벗어난 면은 애초에 "바닥"으로 인식조차 안 함 — 지금 프로젝트가 쓰는 베이크 방식으로는 옆면/아랫면에 몹을 못 세움.
- **`NavMeshSurface`는 됨.** 수직면과 같은 위치·회전을 가진 빈 부모 오브젝트에 `NavMeshSurface`(`collectObjects = Children`)를 붙이고 빌드하니, 그 면 위치에 정확히 16개 정점이 새로 구워짐 — 로컬(면 기준) 좌표계로 베이크되기 때문에, 부모를 면 방향으로 회전시켜두기만 하면 슬로프 계산도 그 로컬 기준으로 정상 동작함.

## 결과 — 미확인 (환경 한계)

`NavMeshAgent.Warp()`와 `SetDestination()`을 에디터 모드(Play 아님)에서 호출했더니 둘 다 실패(`isOnNavMesh=False`, `pathStatus=PathInvalid`) — `NavMesh.SamplePosition()`으로 같은 위치가 유효한 navmesh 지점이라고 확인됐는데도 그랬음. 이건 새 버그라기보단 이 자동화 환경에 이미 기록돼 있던 한계와 같은 종류로 보임(`기획서/CLAUDE.md`: "NavMeshAgent의 실제 이동처럼 네이티브 엔진 틱에 의존하는 건 리플렉션으로도 검증 불가") — `NavMeshAgent`는 내부적으로 Awake/OnEnable 이후 최소 한 번의 엔진 틱이 있어야 정상 동작하는 것으로 보이는데, 이 환경은 에디터 모드에서 그 틱이 안 돎.

**즉 "몹이 실제로 회전된 면 위에서 매끄럽게 추적하며 움직이는지"는 사용자가 직접 Play로 확인해야 함.**

## 추가로 예상되는 후속 작업 (아직 검증 안 함, 예측만)

- `NavMeshAgent.updateRotation`이 기본 켜져 있으면 이동 방향으로 회전할 때 월드 Y축을 기준으로 정렬하려 들 가능성이 높음 — [[CubeSurfaceWalker]]/[[CubeFaceLockedMob]]에서 이미 겪은 "up 벡터가 월드 Y가 아니면 자동 정렬이 깨지는" 패턴과 같은 종류. 실제 적용 시 `updateRotation=false`로 끄고 face normal 기준으로 직접 회전시켜야 할 가능성이 큼.
- 이 프로젝트의 던전 빌드 스크립트(`Floor1CorridorBuilder` 등)는 전부 `bake_navmesh`(레거시 전역 베이크)를 씀 — 큐브 면 구조로 옮기려면 면마다 `NavMeshSurface`를 붙이는 방식으로 베이크 파이프라인 자체를 바꿔야 함.

## 결론

**아키텍처적으로는 가능하다** — `NavMeshSurface`로 면마다 개별 베이크하면 실제로 옆면/아랫면에도 navmesh가 생김(확인 완료). 다만 지금 쓰는 베이크 방식(`bake_navmesh`)은 그대로 못 쓰고, 에이전트 회전/이동이 실제로 매끄러운지는 이 환경에서 자동 검증이 안 돼서 사용자의 직접 Play 테스트가 필요함.
