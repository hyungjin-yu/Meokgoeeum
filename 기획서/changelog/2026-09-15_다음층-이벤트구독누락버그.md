# 다음 층 전환 — C# 이벤트가 씬 저장에 안 남아서 아예 안 걸리던 버그

## 배경

[[changelog/2026-09-15_큐브던전-다음층연결]]에서 방D 클리어 시 다음 층을 재생성하는 기능을 만들고 리플렉션으로 검증까지 마쳤는데, 사용자가 실제로 방A~D를 전부 클리어했더니 **아무 일도 안 일어났다**("이렇게 나와. 2층은 어떻게 넘어가누"). 콘솔에는 4개 게이트가 전부 정상적으로 "클리어!" 로그를 남겼고, `RoomClearGate_D`의 "Stairs도 doorsToOpen도 연결 안 되어 있습니다" 경고(의도된 것)까지 정확히 떴는데, `CubeDungeonProgressionManager` 쪽 로그는 한 줄도 없었음.

## 원인

**C# 이벤트(`+=` 구독)는 Unity가 씬 파일에 저장하지 않는다.** [[CubeFaceRoomBuilder]](에디터 스크립트)가 씬을 짓고 저장하기 "직전"에 `progression.HookGate(roomDGate)`를 호출해서 `RoomClearGate.OnCleared += HandleRoomDCleared` 구독을 걸어놨는데, 이건 그 순간의 인메모리 객체 관계일 뿐 `.unity` 파일에 직렬화되는 대상이 아님. 그래서 사용자가 실제로 Play를 누르는 순간 씬이 **저장된 파일 기준으로 다시 구성**되면서 그 구독은 통째로 사라져있었음 — `RoomClearGate_D`는 클리어를 제대로 감지했지만 `OnCleared`를 들어줄 구독자가 아무도 없어서 그냥 허공에 이벤트를 쏘고 끝난 것.

리플렉션 검증 때는 이 버그를 못 잡았던 이유: 검증을 씬을 새로 짓고 저장한 **같은 Play 세션 안에서** 바로 진행해서, 아직 씬이 파일 기준으로 재구성되기 전(=메모리에 구독이 살아있는 상태)이었음. 사용자처럼 "짓기 → Play 껐다 켜기 → 진짜로 플레이"하는 순서를 거쳐야만 재현되는 버그였음.

## 수정

`CubeDungeonProgressionManager`가 에디터의 일회성 호출에 의존하지 않고, **`Start()`에서 런타임에 스스로 `"RoomClearGate_D"`를 찾아 구독**하도록 변경:

```csharp
private void Start()
{
    var gateGo = GameObject.Find("RoomClearGate_D");
    var gate = gateGo != null ? gateGo.GetComponent<RoomClearGate>() : null;
    if (gate == null) { Debug.LogWarning(...); return; }
    HookGate(gate);
}
```

이러면 씬이 어떻게 저장/로드됐는지와 무관하게 Play를 누를 때마다 항상 스스로 연결됨. `CubeFaceRoomBuilder`의 이제 의미 없는 `HookGate()` 호출도 제거하고 이유를 주석으로 남김.

## 검증

- 재컴파일 에러 없음, 씬 재빌드 성공.
- **완전히 새 Play 세션**에서(이전처럼 같은 세션 안이 아니라) `hookedGate` 필드를 리플렉션으로 확인 — `Start()`가 실제로 `RoomClearGate_D`를 찾아 구독을 걸어둔 것 확인.
- `RoomClearGate.OnCleared`(private 이벤트)를 리플렉션으로 직접 `Invoke()`해서 "게이트가 실제로 클리어를 알릴 때" 경로를 그대로 재현 — 구독자 수 1 확인, 호출 후 `currentFloor`가 1→2로 정상 증가, 플레이어도 방A로 복귀함을 확인. 이번엔 리플렉션으로 매니저 메서드를 직접 부르는 게 아니라 **게이트의 이벤트를 통해서** 도달하는지까지 확인했다는 점이 이전 검증과의 차이.

## 교훈

- **Unity에서 "에디터 스크립트가 런타임 컴포넌트끼리 C# 이벤트/델리게이트 구독을 미리 걸어두는" 패턴은 절대 씬 저장을 못 버틴다.** 이런 구독은 항상 구독하는 쪽의 `Start()`/`OnEnable()`에서 스스로 걸도록 짜야 함 — Inspector에 노출되는 `UnityEvent`라면 직렬화되지만, `public event System.Action` 같은 순수 C# 이벤트는 예외 없이 그때그때 다시 걸어야 함.
- 이번 버그가 리플렉션 검증을 통과했던 건 "같은 세션 안에서 바로 검증"했기 때문 — **"짓기/저장 → 완전히 새로 시작하기 → 실제로 써보기"의 전체 순서를 거치는 검증**이 아니면 이런 종류의 버그(저장에서 안 살아남는 상태)는 못 잡는다는 걸 재확인.
